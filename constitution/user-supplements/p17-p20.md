# 工程憲章補充：階段自主執行與停止條件 v1.1

目前專案出現過多階段內部的人工介入與工作交還，與「工作是為了不用工作」及「事成何必有我」的工程哲學不符。



即日起調整專案執行方式。

## P17：階段內閉環，階段間驗收

每個 Phase 原則上只設置一次人工驗收關卡。



在 Phase 內部，自主完成：

- 設計與技術選型。
- 實作。
- 自我 Code Review。
- 測試與負向控制。
- 故障分析。
- 缺陷修復。
- 回歸測試。
- Git commit。
- 文件更新。
- 驗收證據整理。

上述工作不構成停止點，不需要逐項等待人工確認。



Code Review 發現的問題應直接納入當前工作計畫，自行修復及驗證。

## P18：局部阻塞不等於全局阻塞

發現某項工作受阻時：

1. 記錄阻礙及證據。
2. 判斷能否在現有授權範圍內自行排除。
3. 若無法排除，分析其依賴關係。
4. 繼續其他不受影響的工作。
5. 只有當所有剩餘工作均受到阻礙時，才交還控制權。

不得因為未來階段的功能尚未驗證，而停止當前階段無依賴的工作。

## P19：工程決策自主化

以下事項原則上由 Codex 自行決定：

- 函式庫與依賴選型。
- 資料結構。
- 模組內部介面。
- SQLite 交易與並行策略。
- 錯誤處理方式。
- 測試方法。
- 故障注入方式。
- 資源限制與合理預設值。
- 程式碼缺陷修復。
- 不改變需求與安全邊界的設計調整。

必要時記錄決策理由與替代方案，不需要等待人工批准。



若發現原設計有缺陷，在不改變功能需求、安全要求及授權邊界的前提下，自行修正設計並繼續實作。

## P20：回報不等於交還控制權

進度回報、Git commit、Code Review、測試報告與風險紀錄，均屬於工作過程。



不得因為完成上述事項就結束任務。



回報後應繼續執行當前 Phase 的剩餘工作。



若工具或執行環境存在單次任務限制，應保存可恢復的工作狀態，明確記錄下一個動作，不得將環境限制誤報為階段完成。

## 正式停止條件

只有以下情況允許停止並等待人工決策：



A. 當前 Phase 已完成所有必要驗收，提交階段成果。



B. 必須取得新的權限或外部資源授權，且無其他可繼續工作。



C. 發現重大需求矛盾，無法在既有規格內合理解決。



D. 必須改變已核准的安全邊界或專案範圍。



E. 涉及不可逆操作、正式部署或可能影響其他系統。



F. 所有剩餘工作均已受阻，且已完成合理的自主排查。



一般程式缺陷、測試失敗、技術選型、文件缺漏及局部風險，不構成停止條件。

不得將 Phase 0 結案解讀為產品安全驗收通過。



將 CODE_REVIEW_002 的審查意見納入後續工作計畫，自行決定合理的修復順序。



接著持續完成 Phase 1 的正式認證通訊垂直切片。



除非符合正式停止條件，否則不要在完成單項功能、單次測試、Code Review 或 Git commit 後停止。
