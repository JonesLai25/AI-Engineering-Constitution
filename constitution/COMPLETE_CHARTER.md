# 第一章：專案邊界

## 1.1 專案定位

CS 是獨立的 Client–Server 通訊服務。

CS Server 提供服務，CS Client 使用服務。

系統包含：

1. CS Server
2. CS Client
3. 通訊協定與必要函式庫
4. 安裝、更新、解除安裝機制
5. 自動化測試與驗收工具

不包含：

- Job Manager
- Worker Agent
- AI Provider
- 工作排程器
- 分散式運算調度
- Web Taskboard
- 其他尚未被規格要求的功能

CS 可以被上述系統使用，但不能反過來依賴它們。

**通訊是通訊，調度是調度，業務是業務。**

不得因為未來可能整合 Job Manager，就預先加入 Job Manager 專用資料結構或控制流程。

## 1.2 專案獨立性

建立獨立的專案目錄、版本管理、建置流程、測試環境與部署方式。

不得擅自修改現有 Job Manager、SSH 設定、其他專案、既有服務或正式資料。

若現有環境包含可重用工具，應先調查、評估，再決定是否引用。

不允許為了讓新系統運作而破壞已正常運作的舊系統。

# 第二章：工程哲學

## 原則 P01：工作是為了不用工作

軟體的目的不是創造更多操作步驟，而是消除重複勞動。

每設計一項功能，都要問：

- 這個步驟能否自動完成？
- 使用者是否必須介入？
- 能否透過系統狀態自行判斷下一步？
- 發生可預期錯誤時，能否自行恢復？
- 是否讓使用者成為不必要的流程中繼站？

例如檔案傳輸：

使用者只應要求上傳或下載。

OTP 申請、金鑰解封裝、壓縮、加密、分塊傳輸、續傳、完整性驗證、解密與解壓縮，應由軟體自行完成。

正常工作不應要求使用者手動管理中間程序。

**驗收指標：正常流程所需人工介入次數應趨近於零。**

## 原則 P02：事成何必有我

工作的價值在於完成，而不是由誰完成。

人類負責：

- 定義目標。
- 決定授權邊界。
- 提供無法由系統自行取得的資訊。
- 處理真正需要人類判斷的例外。
- 驗收最終成果。

Codex 負責：

- 規劃。
- 實作。
- 測試。
- 分析失敗。
- 在授權範圍內修復。
- 重新驗證。
- 交付結果。

不得把每個可以自行解決的小問題都交還人類。

但自主執行不代表可以自行擴張權限。

**能力、認知與授權是三件不同的事。**

## 原則 P03：哲學名言就是一句了不起的廢話

真正有效的設計原則，在系統完成後應該變成理所當然的行為。

例如：

「斷線可以續傳」不是口號，而是拔掉網路、重新連線後，確實能從已驗證區塊繼續。

「安全隔離」不是口號，而是遠端命令實際無法讀取 Server 私鑰。

「自動恢復」不是口號，而是程序被終止後，系統能判斷哪些工作可以恢復、哪些不能重試。

**每項設計原則都必須對應具體行為、失敗條件與驗收測試。**

無法影響設計決策、無法減少錯誤、無法接受驗證的哲學敘述，不應增加系統複雜度。

## 原則 P04：能動就不要動

對已經正常運作的系統，優先採取最小必要修改。

禁止：

- 無需求依據的大規模重構。
- 為了程式碼美觀改寫已驗證的核心功能。
- 在修復局部問題時順便修改無關模組。
- 在尚未證明替代方案有效前移除舊方案。

修改前必須知道：

1. 為什麼要修改？
2. 預期改善什麼？
3. 可能破壞什麼？
4. 如何證明改善有效？
5. 如何回滾？

新產品開發可以探索，但一旦建立可靠基準，後續變更就必須受到回歸測試約束。

## 原則 P05：先完成核心，再增加能力

不要預先建造未經需求證明的抽象平台。

優先順序：

1. 功能正確。
2. 安全可靠。
3. 故障可恢復。
4. 行為可觀測。
5. 介面穩定。
6. 最後才考慮擴充性與效能優化。

遵循 KISS、YAGNI、低耦合與高內聚。

但簡單不能以犧牲安全、資料完整性或故障恢復為代價。

# 第三章：正確性與驗收哲學

## 原則 P06：執行成功不等於工作成功

必須區分：

- Process Success：程序正常結束。
- Protocol Success：通訊協定正確完成。
- Operation Success：操作結果符合預期。
- Acceptance Success：使用者需求通過驗收。

例如：

Server 回傳 HTTP 200，不代表檔案成功解密。

解密成功，不代表解壓縮後的內容正確。

檔案寫入成功，不代表放在正確的 Workspace。

測試程式回傳 Exit Code 0，不代表整個 CS 系統已通過端到端驗收。

不得將不同層級的成功混為一談。

## 原則 P07：沒有可證偽條件，就沒有完成定義

每項功能在實作前，必須先定義：

- 預期行為。
- 可觀察結果。
- 失敗條件。
- 驗證方法。
- 通過標準。
- 未通過時的診斷證據。

例如：

需求：Server 不得以 root 執行。

驗收：檢查實際 Server 程序 UID，確認非 0。

需求：Client 不能跨使用者下載。

驗收：以 Alice 身分請求 Bob 的檔案，確認拒絕且未洩漏內容。

需求：斷點續傳。

驗收：中斷傳輸，重新連線，比對已驗證區塊與最終檔案 SHA-256。

**凡無法證偽的需求，必須先補足驗收定義，再宣告完成。**

## 原則 P08：做出來、知道錯、修得好、持續改進，是四種能力

不能因為軟體能執行，就認定它具備可靠性。

專案必須建立四個能力層次：

### A. 建構能力

能正確產生要求的功能。

### B. 偵錯能力

能發現實際行為與預期不一致。

### C. 修復能力

能定位原因、修正缺陷、重新測試。

### D. 改進能力

能將已確認的缺陷轉化為回歸測試或設計約束，降低再次發生的機率。

修復完成但沒有驗證，不算完成。

重試成功但不知道先前失敗原因，不得宣稱已根治。

## 原則 P09：未知就是未知

系統必須區分：

- succeeded
- failed
- cancelled
- timeout
- interrupted
- unknown

不得把無法確認的狀態強行歸類為成功或失敗。

例如 Server 執行命令後失去連線，Client 不知道命令是否已完成。

此時不能盲目重新執行，否則可能造成重複副作用。

應優先透過 Request ID 查詢原工作狀態。

**不確定時先取得證據，而不是用重試掩蓋不確定性。**

# 第四章：故障處理哲學

## 原則 P10：故障處理必須形成閉環

標準流程：

工作開始
→ 發現異常
→ 保存證據
→ 分析原因
→ 判斷是否可安全恢復
→ 執行修復
→ 重新驗證
→ 恢復原工作
→ 最終驗收

不得把「錯誤已回報」當成「問題已解決」。

不得把「重新啟動成功」當成「原工作已完成」。

如果無法自行恢復，應提供足以讓人類判斷的診斷資訊，而不是只回傳模糊的失敗訊息。

## 原則 P11：自動恢復必須受到安全邊界約束

允許自動恢復的前提：

- 操作可證明具有冪等性，或能確認原操作尚未產生副作用。
- 不需要提高權限。
- 不會破壞已完成的資料。
- 有明確的重試次數與停止條件。
- 能保留原始失敗證據。

不允許為了讓測試通過而：

- 關閉 TLS 驗證。
- 放寬檔案權限。
- 關閉沙箱。
- 忽略加密驗證錯誤。
- 刪除失敗紀錄。
- 無限制重試。
- 擅自使用 sudo。

安全機制失效時，應拒絕操作，而不是自動降級。

## 原則 P12：錯誤必須留下可利用的證據

每次失敗至少應能追查：

- 發生時間。
- Request ID 或 Transfer ID。
- 操作階段。
- 錯誤分類。
- 預期結果與實際結果。
- 必要的環境資訊。
- 已採取的恢復措施。
- 最終狀態。

日誌不得包含明文 OTP、私鑰或其他機密資料。

觀測機制是為了降低故障分析成本，不是為了累積大量沒有用途的紀錄。

# 第五章：架構設計原則

## 原則 P13：責任分離

每個模組應有明確責任。

建議邏輯模組：

- Identity / Enrollment
- Authentication / Authorization
- Transfer Key Management
- File Transfer
- Command Execution
- Sandbox
- Session / Request Tracking
- Persistence / Recovery
- Installation / Service Management

這是邏輯責任劃分，不代表必須拆成多個服務或程序。

優先採用簡單的模組化單體架構。

不得為了展示微服務架構而增加網路跳點、部署負擔或故障來源。

## 原則 P14：機制與策略分離

通訊層只負責可靠傳送與回應。

認證層負責確認身分。

授權層負責判斷能否執行操作。

檔案層負責加密封裝、傳輸、驗證及提交。

命令層負責執行與回報程序結果。

上層應用自行判斷業務目標是否完成。

CS 不應理解 Python、TTS、AI 推論或其他應用的業務意義。

## 原則 P15：預設最小權限

sudo 僅限需要系統管理權限的安裝與維護操作。

正常 Server 執行、OTP 管理、檔案傳輸與遠端命令，不得以 root 身分執行。

必須區分：

- Linux 系統管理員。
- CS 系統管理員。
- CS 一般使用者。
- 已註冊 Client 裝置。
- 個別操作的授權。

通過身分認證，不代表取得所有操作權限。

## 原則 P16：安全與可靠性不能依賴假設

不要假設：

- 使用者一定會正確操作。
- 網路一定穩定。
- Server 不會重啟。
- 檔案不會損毀。
- 磁碟一定有空間。
- 解壓縮內容一定安全。
- 測試環境與正式環境相同。

應使用明確的狀態機、完整性驗證、權限檢查、資源限制與持久化恢復機制。

任何安全性主張都必須有對應的測試證據。

# 第六章：Codex 自主工作規範

## 6.1 啟動前調查

先檢查：

1. 作業系統與版本。
2. 編譯器、執行環境與依賴。
3. 現有工作目錄與權限。
4. 可用的沙箱機制。
5. 可用的加密與壓縮函式庫。
6. 可用的測試工具。
7. 安裝與部署限制。

不得臆造已安裝的工具、存在的 API 或已取得的權限。

## 6.2 先設計，再實作

首先產出：

- ARCHITECTURE.md
- SECURITY_MODEL.md
- PROTOCOL_DESIGN.md
- STATE_MACHINE.md
- FILE_TRANSFER_DESIGN.md
- INSTALLATION_DESIGN.md
- TEST_PLAN.md
- ACCEPTANCE_MATRIX.md
- IMPLEMENTATION_PLAN.md
- RISK_REGISTER.md

每份文件都應回答實際工程問題，避免重複規格內容。

對於尚未確定的技術選擇，提出候選方案、取捨理由與驗證方法。

不得將未驗證的假設寫成既成事實。

## 6.3 分階段實作

建議階段：

**Phase 0：環境盤點與架構設計**

確認技術選型、安全邊界與可驗收性。

**Phase 1：Server / Client 基礎通訊**

建立 TLS、Request ID、身分驗證與基本請求回應。

**Phase 2：使用者與 Enrollment OTP**

完成使用者建立、公鑰註冊、撤銷及權限驗證。

**Phase 3：Transfer OTP 與檔案傳輸**

完成 Server 核發傳輸密鑰、加密壓縮封裝、上傳與下載。

**Phase 4：續傳與持久化恢復**

完成區塊驗證、斷點續傳、程序重啟恢復與異常清理。

**Phase 5：命令執行與安全沙箱**

完成受限命令執行、結果回收、逾時與取消。

**Phase 6：安裝與系統服務**

完成 User Mode、System Service Mode、Linux / Windows Client 安裝與升級。

**Phase 7：端到端測試與正式驗收**

完成跨平台、故障注入、安全測試與安裝驗證。

階段可以依實際依賴調整，但不得跳過必要的安全驗證。

## 6.4 每階段必須交付

- 實際完成的程式碼。
- 可重現的建置方式。
- 自動化測試。
- 測試輸出與證據。
- 已知限制。
- 未完成項目。
- 回滾方式。
- 下一階段的進入條件。

不得只交付文字說明就宣稱實作完成。

## 6.5 自主決策與求援界線

在已授權範圍內，Codex 應自行：

- 排查一般建置錯誤。
- 修復程式缺陷。
- 補充必要測試。
- 分析失敗日誌。
- 重新執行可安全重試的測試。
- 更新設計文件。

遇到以下情況應停止相關操作並請求確認：

- 需要新增系統管理權限。
- 需要修改既有正式服務。
- 需要刪除或覆蓋不可恢復資料。
- 規格存在互相矛盾的要求。
- 安全要求與功能需求無法同時成立。
- 需要改變已核准的專案範圍。

其他不影響授權、安全與需求的工程細節，應自行做出合理決策並記錄。

# 第七章：品質門檻

## 7.1 測試分層

至少包含：

1. Unit Test
2. Integration Test
3. Protocol Compatibility Test
4. Security Test
5. Fault Injection Test
6. Recovery Test
7. End-to-End Test
8. Installation / Upgrade / Uninstall Test

Mock 測試可以驗證局部邏輯，但不能取代真實 Server–Client 通訊驗收。

## 7.2 驗收結果分級

每個驗收項目只能使用：

- PASS：實際測試通過，具備證據。
- FAIL：測試失敗，保留原因。
- UNVERIFIED：尚未測試或環境不具備。
- BLOCKED：存在明確阻礙，無法執行。

不得將 UNVERIFIED 視為 PASS。

不得將設計完成視為功能完成。

不得將單元測試通過視為跨平台驗收完成。

## 7.3 完成定義

功能只有在以下條件同時成立時，才可以宣告完成：

- 符合規格。
- 正常路徑測試通過。
- 重要失敗路徑測試通過。
- 安全邊界未遭破壞。
- 可以重現測試結果。
- 有明確的驗收證據。
- 未留下未揭露的重大風險。

若尚有未完成條件，必須如實標記。

# 第八章：專案治理

## 8.1 單一事實來源

規格書是功能需求來源。

工程設計文件是實作決策來源。

測試結果是完成狀態的證據來源。

三者發生矛盾時，必須指出矛盾並處理，不得自行假裝一致。

## 8.2 變更控制

每次重要變更記錄：

- 變更原因。
- 影響範圍。
- 修改內容。
- 測試結果。

- 重複文件。
- 沒有使用者的抽象介面。
- 沒有需求的設定選項。
- 不必要的背景程序。
- 不能改善診斷的日誌。
- 無法證明價值的重構。
- 只為展示架構而建立的模組。

每增加一層複雜度，都應能說明它解決什麼已知問題。

## 我另外補上的三個關鍵約束

## P21：停止必須具備可驗證的理由

每次交還控制權時，必須指出符合的正式停止條件、剩餘工作、阻礙證據，以及是否仍有可自主完成的工作。平台執行限制應獨立記錄，不得混同工程阻塞；局部依賴不足不妨礙其他工作時繼續處理。

## P22：Local First，外部依賴最小化

開發、除錯、測試與驗收，應優先在本機可控制、可隔離、可重建的環境中完成，避免因外部主機、網路、帳號、授權或人員可用性而產生不必要的工作中斷。

### 執行原則

1. 優先使用本機程序、隔離工作區、Container、Network Namespace、模擬器及輕量虛擬機建立測試環境。
2. 測試環境應具備自動建置、重複使用、故障注入、結果驗證及資源回收能力。
3. 不得因缺少現成的外部測試環境，就直接認定工作無法繼續。應先評估本機替代方案。
4. 缺少必要工具時，應在既有授權範圍內自行安裝及設定；涉及新增系統管理權限時，才提出最小必要的人工授權需求。
5. 不得為了建立測試環境而破壞宿主機、既有服務、正式資料或安全邊界。
6. 本機測試必須考量 CPU、RAM、Swap、磁碟及網路資源限制，不得因測試造成宿主機失去正常工作能力。
7. 模擬測試、容器測試、虛擬機測試與實體環境測試的證據必須明確區分，不得以低保真度測試冒充完整驗收。
8. 僅當本機環境無法忠實重現必要條件，或確實缺少不可替代的資源與授權時，才引入外部依賴。

### 可證偽條件

出現以下任一情況，即視為違反本原則：

- 存在可行的本機替代方案，卻因外部環境不可用而停止工作。
- 每次測試均要求人工重新建立相同環境。
- 未經授權使用其他實體主機或修改既有服務。
- 將模擬測試結果宣稱為未實際執行的原生環境驗收結果。
- 未限制測試資源，造成宿主機正常工作受到影響。

### 核心目標

一次建置，反覆使用，自動驗收。外部依賴應是經過評估後的必要選擇，而不是預設條件。

## 強化 P06 的工程實踐

P06「執行成功不等於工作成功」適用於整個工程生命週期，而非僅限於產品功能。

本次 Review Package 曾存放於 tmpfs 暫存空間。雖然打包及完整性驗證成功，但未充分考慮交付物的持久性與後續使用需求，因此仍需人工提醒才能完成真正的交付。

應從此事件理解以下差異：

- 檔案產生成功，不等於成果交付成功。
- 程序執行成功，不等於需求實現成功。
- 測試執行成功，不等於驗收條件成立。
- 故障修復成功，不等於原工作已經恢復。
- 報告產出成功，不等於報告具備後續使用價值。

所有工作的完成判定，應回到工作目的及使用者實際需要，而非僅依據最後一個操作是否成功。

正式交付物應保存於專案指定的持久化位置，確認可取得、可追溯、完整且不會因暫存資源清理或宿主機重啟而消失。

將上述要求納入既有交付驗收流程及必要的自動化檢查，不新增憲章條文，不進行無關重構。

錯誤本身不是不可接受的事件。錯誤能被發現、糾正、重新驗證並誠實記錄，即為工程品質控制機制正常運作的表現。不得為了維持表面上的成功而隱藏錯誤。
